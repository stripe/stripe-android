Summary: The Mobile Checkout Elements add-discounts guide presents server coupons and customer promotion codes as available without stating discount-specific prerequisites. On an otherwise working US test-merchant mobile_elements integration, following either creation recipe fails with HTTP400; omitting the creation flag allows checkout but public applyPromotionCode fails because Checkout Client rejects promotion_code. Merchants cannot reach the documented discounted checkout flow in this configuration.

Repro: Use SDK8cbb695eabcafa957a86c24e1f025643979a500a and the US merchant at the source-verified test backend with Stripe-Version2026-08-26.preview. Create the valid USD120 guest Session shown in [creation-allow-promotion.json](bug-bash/discounts/creation-allow-promotion.json). Removing allow_promotion_codes yields HTTP200. Adding only allow_promotion_codes:true yields “You can not pass `allow_promotion_codes` in `modeless` mode.” Instead adding discounts:[{coupon:fresh_valid_coupon}] yields the same modeless rejection for discounts. In the successful plain Session, call controller.applyPromotionCode with the fresh25% code: “Received unknown parameter: promotion_code”. The guide explicitly requires allow_promotion_codes:true and advertises both coupon creation and apply/remove: [verified excerpts](bug-bash/docs-driven/DISCOUNTS_DOCS_EXCERPTS.md).

Test: [backend_contract_probe.py](bug-bash/discounts/backend_contract_probe.py), after [provision.py](bug-bash/discounts/provision.py), passed its assertions of the observed failure contract: plain creation200, flag-only/coupon-only creation400, valid-uppercase apply and empty remove400 parameter_unknown/promotion_code. These are expected failure observations, not passing discount behavior. [Sanitized results](bug-bash/discounts/backend-contract-results.json). Physical Pixel6a/API36, installed baseDebug, showed [flag error](bug-bash/discounts/allow-promotion-error.png), [coupon error](bug-bash/discounts/server-coupon-error.png), and [public apply error](bug-bash/discounts/apply-unknown-parameter.png); all screenshots inspected. Independent [Session retrieval](bug-bash/discounts/backend-percent.json) remains open/unpaid/not_started,total12000 after apply. [GitHub duplicate search](bug-bash/discounts/github-duplicate-search.json), --state all, and local reports found no matching root cause. No successful discounted control/payment or restriction validation claimed.

Elaboration: Backend [source evidence](bug-bash/discounts/BACKEND_CONTRACT_EVIDENCE.md) at001bc4512d28a43acf2edefa2491bd853cd84372 requires checkout_unified_mode_development for modeless discounts and allow_promotion_codes. The complete Checkout Client update schema has no promotion_code field, matching the real parameter_unknown response. SDK CheckoutElementsController.applyPromotionCode delegates to CheckoutSessionRepository.applyPromotionCode, which sends that field to /v1/checkout_client/{id}/update; remove sends the same field empty. This report is a documentation availability/prerequisite gap for an unfinished/gated preview flow, not a newly established SDK behavioral regression or claim about every merchant.
