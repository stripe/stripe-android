Summary: The customer-email guide says overriding a server-provided email returns an error, but Android updateEmail returns Succeeded and keeps the original server email. A merchant following the documented error contract can display success for an email change that will not affect checkout.

Repro: Create a test-mode mobile_elements Checkout Session with customer_email=foundation.bugbash@example.com, initialize CheckoutElementsController, then call updateEmail("changed.foundation@example.com"). The guide at https://docs.corp.stripe.com/payments/mobile/checkout-sessions/build-a-checkout-page?platform=android#collect-email says this attempt returns an error. Actual result is OperationResult.Succeeded; session.email remains the server-provided value. On the physical Pixel, use bug-bash/docs-foundation/card-control.json, create a session, replace Email with changed.foundation@example.com, and tap Update email: the playground reports “Email updated”.

Actual updateEmail (CheckoutElementsController.kt:269) stores local collectedDetails.email and returns success without a network call. CheckoutSessionMappers.kt prefers fixedEmail over collectedEmail; CheckoutSessionConfirmationInterceptor.kt only sends collectedInformation.email when fixedEmail is absent. Existing tests establish this as deliberate Android behavior. The documentation should accurately describe that outcome or the SDK contract must be deliberately changed; this report does not propose changing the immutable-email rule.
