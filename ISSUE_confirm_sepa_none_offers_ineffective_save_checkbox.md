Summary: A merchant enables saving for a Checkout Elements session but sets `payment_method_options[sepa_debit][setup_future_usage]=none`, for example to allow saved cards while keeping SEPA payments one-time. Android still offers SEPA's "Save payment details to [merchant] for future purchases" checkbox. The customer can check it and complete confirmation, but the SEPA method is not attached to the customer and is absent in a fresh checkout even when all redisplay values are allowed. The checkbox promises a save that this accepted configuration cannot perform.

Repro: Create a test customer with an email. Create a Checkout Session using `ui_mode=mobile_elements`, EUR one-time items, `allowed_payment_method_types=[card,sepa_debit]`, that customer, `saved_payment_method_options[payment_method_save]=enabled`, and `payment_method_options[sepa_debit][setup_future_usage]=none`. Configure `CheckoutElementsController` with a Payment Element. Choose SEPA, enter synthetic name/email and test IBAN `DE89370400440532013000`, check the save checkbox, and confirm. Create a fresh session for the same customer with `saved_payment_method_options[allow_redisplay_filters]=[always,limited,unspecified]`: the SEPA method is absent. The actual PaymentIntent has top-level `setup_future_usage=off_session` but retains SEPA PMO SFU `none`; the expanded PaymentMethod has `allow_redisplay=always` and `customer=null`. Removing only the SEPA `none` option makes the checked-save control attach the method and return it in fresh sessions. `payment_settings[setup_future_usage]=off_session` is not required; a separate test with that setting reproduced the same issue.

Elaboration: `CheckoutSessionResponseJsonParser` correctly maps the backend's effective SEPA SFU `none` into the deferred Intent's payment-method options. `CreateCustomerMetadata` also correctly maps the session-wide save option to `PaymentMethodSaveConsentBehavior.Enabled`. `SaveForFutureUseHelper.isSaveForFutureUseValueChangeable`, however, returns only `hasCustomerConfiguration` for Enabled consent and never checks the selected method's explicit `none`. `SepaDebitDefinition` consequently creates a `SaveForFutureUseElement`. The replay uses the public controller's loaded metadata, toggles that real form controller, constructs a matching selection and converts it into a confirmation option, and exercises the real `CheckoutSessionConfirmationInterceptor`/`CheckoutSessionRepository`; request matching verifies `collected_information[save_payment_method]=true` and `payment_method_data[allow_redisplay]=always`. The server correctly retains the merchant's per-method override and does not attach the method. This is an ineffective save offer, not a lost save flag, local saved-method filtering, a failure to confirm, or an incorrect backend SFU precedence rule.
