Summary: The Checkout Elements migration guide tells merchants to retain supported payment-level parameters through payment_intent_data, but the required modeless mobile_elements Session rejects that container. Migrating the supported setup_future_usage=off_session setting as instructed prevents Session creation; the same setting succeeds through payment_settings.

Repro: Use the US test merchant and Stripe-Version2026-08-26.preview on the [source-verified backend](bug-bash/docs-driven/BACKEND_PROXY_ROUTES.md). Create a valid test Customer with migration.bugbash@example.com. Create the guide's USD1099 T-shirt using items/one_time_price, ui_mode=mobile_elements, that Customer, and no mode. Plain creation succeeds. Add only payment_intent_data:{setup_future_usage:"off_session"}: HTTP400, “You can not pass `payment_intent_data` in `modeless` mode.” Replace only the container name with payment_settings: HTTP200 and payment_settings.setup_future_usage=off_session in the response. [Exact sanitized comparison](bug-bash/migration/backend-contract-results.json).

Actual exit0 verifies plain200/current200/legacy400 with one fresh valid test Customer and otherwise identical requests; this is a passing reproduction of the documentation failure, not successful legacy behavior. Keys and client secrets remain in memory and are not retained. Current-container support is additionally established by the earlier [saved-methods real payment and subsequent limited redisplay](bug-bash/saved-methods/RUN_NOTES.md). No new SDK test or device payment needed for this server creation error. The observed rejection names the entire legacy container, while the current container accepts and echoes the identical supported parameter. This is a concrete migration documentation contract problem in the tested preview configuration, not an unsupported setup-mode request, invalid Customer, SDK confirmation bug, or proof of universal merchant availability.
