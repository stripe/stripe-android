Summary: Updating a mutable Checkout Session email after selecting a new card silently clears the selected payment option, even when updateEmail returns Succeeded. A merchant that collects or edits checkout email after card entry cannot confirm until the customer reopens the Payment Element and selects the retained card again.

Repro: On stripe-android 8cbb695eabcafa957a86c24e1f025643979a500a, create a guest mobile_elements Checkout Session without server customer_email or Customer.email, configure Payment Element, and select test Visa 4242424242424242 (12/30, CVC 123, US 94103). Before any confirmation, await controller.updateEmail("before.confirm.email@example.com"). Result is Succeeded and session.email changes, but session.paymentOption becomes null. Confirm now fails with “Something went wrong”; backend remains open/unpaid/not_started. Reopen Select: card fields remain. Continue restores selection, and Confirm completes the same Session. The example configuration is [mutable-email.json](bug-bash/email-lifecycle/mutable-email.json). The same reset was observed after a missing-email failure with 3155 and after clearing a default email. A same-value email update preserves the selection.

Test: Apply [selected-card-email-regression.patch](bug-bash/email-lifecycle/selected-card-email-regression.patch) and run ./gradlew :paymentsheet:testDebugUnitTest --tests 'com.stripe.android.checkout.CheckoutElementsControllerTest.email bugbash*'. The changed-email preservation regression fails as intended because the public paymentOption is null; the unchanged-email control passes (2 tests, 1 expected failure, 0 errors/skips; Gradle exit 1). This uses the production Dagger controller graph, real Checkout mapping/reload/selection chooser, and NetworkRule init fixture, seeding only the prior card selection through the real state holder. Elaboration: CheckoutElementsController.updateEmail stores collectedDetails.email, then withCheckoutState reloads the existing Session. CheckoutConfigurationMappers.toBillingDetails maps checkout collectedEmail into PaymentSheet defaultBillingDetails.email. CheckoutStateLoader passes the carried selection and this newly constructed CommonConfiguration into DefaultEmbeddedSelectionChooser. Its shouldUsePreviousSelection rejects the card because CommonConfiguration.containsVolatileDifferences includes defaultBillingDetails; for this guest Session the loader has no replacement selection, so CheckoutStateLoader publishes null. The generic Embedded chooser intentionally treats changed billing defaults as a reason to invalidate selection; the Checkout integration makes a checkout-email edit trigger that policy. The [email guide](https://docs.corp.stripe.com/payments/mobile/checkout-sessions/build-a-checkout-page?platform=android#collect-email), verified in [Markdoc excerpts](bug-bash/docs-driven/EMAIL_LIFECYCLE_DOCS_EXCERPTS.md), explicitly describes checkout email as separate from payment-method billing email and instructs merchants to call updateEmail on edits. No failed confirmation, presentation overlap, race, new Session, or process death is required. Waiting for the completed operation does not fix it; reselecting does. This report concerns the reachable Checkout behavior, not a proposed change to generic Embedded invalidation policy. Relevant files are paymentsheet/src/main/java/com/stripe/android/checkout/{CheckoutElementsController.kt,CheckoutConfigurationMappers.kt,CheckoutCommonConfigurationFactory.kt,CheckoutStateLoader.kt}, paymentelement/embedded/content/EmbeddedSelectionChooser.kt, and common/model/CommonConfiguration.kt.
